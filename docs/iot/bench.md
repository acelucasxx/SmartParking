## 准备

### 环境

DTU 走 4G，**必须连得到公网上的 EMQX**，开发机上的本地环境不行。任选其一：

- 测试环境（INF 线部署后）。
- 临时云主机跑 [deploy/local](../../deploy/local/README.md) 的 compose，安全组只对现场出口 IP 放行 1883，联调结束即关闭。1883 是明文，只用于联调；生产只开 8883（[device-access.md](device-access.md)）。

业务服务与 EMQX 同机启动，EMQX 的认证回调要能访问业务服务。业务服务刚启动的几秒内，EMQX 的认证后端可能还标记为不可用，设备与业务服务会被拒连一两次，随后重连成功，属正常现象。

### 登记设备、暂停定时查询

```sql
INSERT INTO device (sn, imei, model, batch_no, activate_code_hash)
VALUES ('BENCH-<imei>', '<imei>', 'SP-G1', 'BENCH', 'x');

-- 联调期间关闭定时查询：协议没有请求编号，业务服务的查询回包会被工具当成自己的
UPDATE system_config SET config_value = '0' WHERE config_key = 'status_poll.interval_minutes';
```

结束后把间隔改回 `5`。设置缓存 30 秒，改完稍等再开始。

### 配置 DTU

用厂家的配置工具写入（参数名以厂家工具为准）：

| 项 | 值 |
| --- | --- |
| 工作模式 | MQTT 透传 |
| Broker | 上面 EMQX 的公网地址，端口 1883 |
| 客户端 ID | `dtu-<imei>` |
| 用户名 | `<imei>` |
| 密码 | `./gradlew :dtu-bench:run --args="password --imei <imei>"` 的输出（平台密钥要与业务服务一致，非本地环境用 `--secret-key` 或环境变量 `DEVICE_SECRET_KEY`） |
| 订阅 | `parking/down/<imei>`，QoS 1 |
| 发布 | `parking/up/<imei>`，QoS 1 |
| Clean Session | 开（若只能关，在记录里写明，见步骤 6） |
| 串口 | 按闸板协议文档（波特率、数据位等） |
| 串口打包时间 / 长度 | **先用出厂默认**，记录默认值；步骤 5 再调 |
| 心跳间隔 | 记录默认值 |

## 步骤

以下命令在 `server/` 目录执行；连接测试环境时加 `--broker tcp://<host>:1883 --password <云端账号密码>`，或设置环境变量 `BROKER`、`MQTT_SERVER_PASSWORD`。每次运行都会在当前目录生成 `bench-<imei>-<时间>/`，内含 `report.md`、`samples.csv`、`uplinks.csv`（每条上行的到达时刻与原始字节）。

1. **上电上线**：给设备上电，记录从上电到业务服务日志出现 `<imei> 上线` 的时间。上线后业务服务会立即查询一次状态（IOT-10），日志里能看到 `↓ … D0 C0` 与回包。

2. **静置监听 10 分钟**（问题 4）：

   ```bash
   ./gradlew :dtu-bench:run --args="listen --imei <imei> --minutes 10"
   ```

   不做任何操作。期间收到的“非 RS485”条目即 DTU 心跳 / 注册包，记录其内容与间隔。

3. **非 App 动作**（问题 5）：再开一次 `listen`，期间在现场依次用遥控器抬杆、落杆，触发地感，等延时自动关。收到状态帧说明闸板会主动上报，记录原因码；什么都没收到说明不会。

4. **剧本 20 轮**（问题 1、2、3）：

   ```bash
   ./gradlew :dtu-bench:run --args="run --imei <imei> --rounds 20"
   ```

   每轮先复位到关闸到位，再依次查询、查版本、抬杆、落杆。抬杆 / 落杆每 300 ms 查询一次直到到位，到位时延的分辨率就是这个间隔。3 台样机各跑一次。

5. **粘包压力**（问题 3）：`--poll-ms 100` 再跑 10 轮。查询更密时，回显帧与状态帧更容易被 DTU 打成一包。若出现粘包 / 拆包，调整 DTU 串口打包时间后重跑，记录参数与结果。

6. **掉线与离线不排队**（问题 6、7）：
   - 设备断电，记录业务服务多久记为断开（keepalive 超时），`device_runtime.online_state` 变为 `SLEEP`。
   - 断电期间用 `run --rounds 1` 下发（会全部超时），20 秒后再上电：闸杆**不应动作**。云端下行带 15 秒过期时间，过期即被 EMQX 丢弃；若闸杆动了，说明 DTU 用了持久会话且过期未生效，立即记录并反馈。
   - 恢复上电，记录重新上线的时间。

7. **弱信号**（可选）：在地库实际安装位置重复步骤 4，记录信号强度与时延变化。

## 通过标准（G1）

- 3 台样机查询、查版本、抬杆、落杆成功率 100%。
- 抬杆 / 落杆到位 P95 ≤ 5 秒（PRD 10 非功能需求，含 4G 往返）。
- 步骤 6 中离线期间的指令上线后不执行。
- 粘包 / 拆包、心跳、主动上报三项有明确结论（有或无都算结论）。

## 结论如何落到代码

云端 `UplinkDispatcher` 目前假定一条消息恰好一帧，不是一帧的整条丢弃并记 WARN，**也不刷新 `last_seen_at`**。

| 联调发现 | 处理 |
| --- | --- |
| 有粘包 / 拆包，调打包参数可消除 | 把参数写进 DTU 出厂配置（EXT-07），云端不改 |
| 有粘包 / 拆包，调参数消除不了 | 云端按 `PayloadAnalyzer` 的规则拆帧 / 拼帧后再分发 |
| 心跳发到上行主题 | 识别心跳格式，计入 `last_seen_at`（PRD 8.5“任意上行”）；可考虑放宽定时查询（PRD 8.7） |
| 闸板主动上报 | 状态帧照常处理；可放宽定时查询到 30 分钟或关闭，IOT-13 调整“约”时间标注 |
| 实测动作时延明显偏离 1.2 秒 | 复核 15 秒超时与 300 ms 轮询间隔 |
