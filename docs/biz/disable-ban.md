# 设备禁用与用户封禁

对应 BIZ-16（PRD 5.8）。禁用 / 启用设备见 [admin-ops.md](admin-ops.md)（BIZ-10）；封禁 / 解封用户的代码在 `server/admin` 的 `AdminUserOps`，接口见契约 [openapi-admin.yaml](../api/openapi-admin.yaml) 的 user 分组。两者的业务效果都由各接口按当前状态判定，不改绑定与授权数据，所以恢复后一切照旧。

## 设备禁用

`POST /api/admin/devices/{deviceId}/disable`、`/enable`：超级管理员、运维。原因必填，写操作日志 `DEVICE_DISABLE` / `DEVICE_ENABLE`。

| 接口 | 禁用时 |
| --- | --- |
| 车位列表、设备详情、状态、操作记录 | 照常，卡片与详情的 `enabled = false`，小程序显示“设备已停用，请联系客服” |
| 抬杆 / 落杆（含蓝牙票据） | 20002 |
| 邀请、修改被授权人有效期或备注、发起转让 | 20002 |
| 接受邀请、接受转让、扫码绑定 | 20002 |
| 成员列表、撤销成员、退出授权、取消邀请 / 转让、解绑、改名称 | 照常（收尾操作不拦） |

- 绑定关系、被授权人、待接受的邀请与转让卡片都保留；启用后在有效期内照常可用。
- 判定在统一权限判定（[permission.md](permission.md)）里：`CONTROL`、`OWNER_ENABLED` 两级要求设备启用；接受邀请 / 转让、绑定在各自事务内锁设备后再检查一次。

## 用户封禁

`POST /api/admin/users/{userId}/ban`、`/unban`：超级管理员、客服。

| 情况 | 结果 |
| --- | --- |
| 原因缺少或去首尾空白后不足 2 个字符 | 40020 |
| 原因超过 255 个字符 | 10001 |
| 用户不存在 | 10004 |
| 重复封禁 / 重复解封 | 成功，操作日志明细 `changed = false` |

成功与失败都写操作日志 `USER_BAN` / `USER_UNBAN`，对象类型 `APP_USER`。

封禁只把 `app_user.status` 改成 `BANNED`，效果：

- **本人**：登录和全部 C 端接口返回 403 / 10010“账号已停用”，退出登录除外。每个请求都查库，封禁、解封即时生效，不需要作废会话。
- **作为主人的设备**：不解绑。被授权人在有效期内照常查看、控制；如需处置，走客服强制解绑。
- **作为被授权人的授权**：保留但无法使用（被上一条拦住）。
- **其发出、尚未被接受的邀请与转让卡片**：预览显示 `CANCELLED`，接受返回 30014 / 30022。卡片本身不作废，解封后在有效期内恢复可用。封禁的账号不应再通过已发出的卡片改变设备的成员或归属。
