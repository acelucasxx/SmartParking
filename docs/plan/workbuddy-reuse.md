## 2. 可直接借用的设计

这些做法在 WorkBuddy 里已经验证过，新代码应保留：

- 编解码是无 Spring 依赖的纯函数，结构错误抛 `ProtocolException`，未知状态码 / 原因码记为 `UNKNOWN` 不抛异常。
- MQTT 载荷全程 `byte[]`，只在日志里转十六进制；按 UTF-8 处理会把 `FD` / `FA` 换成占位符。
- 查询指令数据位固定 `C0`，并在代码注释里写明原因（插枪状态下落杆静默失效）。
- 先落库再下发；下发异常时立即把指令置为终态，不留悬挂记录。
- Redis 锁解锁用“比较 token 再删除”的 Lua 脚本，避免误删他人的锁。
- `PendingReplies` 把异步上行帧配对给等待者；无论完成、超时还是异常都在 `whenComplete` 中摘除，避免泄漏；断线时 `failAll` 让等待方立刻失败。
- 状态未变化不写 `device_event`，避免 300 ms 轮询把事件表刷满。
- 未登记 IMEI 只记日志、按 IMEI 10 分钟节流告警，不回包。
- 定时任务内部捕获全部异常，避免调度线程停止。
- 导入校验是纯函数：一次只报一个错，报表格从左到右第一个错；文件内重复提示“与第 N 行重复”。

## 3. 逐项评估

### 3.1 RS485 编解码（改造）

可复用：

- 帧头尾常量、`encode` 的长度计算（注释记录过少一个字节导致空帧的历史 bug）。
- 长度 5–8 字节、首尾标志、超长提示“疑似粘包”的校验。
- 状态码、原因码、车位码的查表与归一（01/02、03/04、06/07 归为同一触发方式）。
- 10 个单测样例，包括 PRD 8.2 的 `FD 00 01 09 16 11 FD FA`。

必须修改：

| # | 问题 | 依据 | 改法 |
| --- | --- | --- | --- |
| 1 | `decode` 只有上行语义，不区分方向；下行查询帧 `FD 00 01 D0 C0 FD FA` 会被解成 UNKNOWN | PRD 8.2“解析必须显式区分方向，不得靠长度猜” | 拆成 `decodeUplink` / `decodeDownlink`，或传入 `Direction` 参数；模拟器侧已有同样的教训注释 |
| 2 | 原因码 `0x16` 标为“扫码开闸” | PRD 8.3：16 = 平台指令 | 映射到契约 `TriggerSource.APP` |
| 3 | `GateStatus.lockState()` 用 up / down 表示落杆 / 抬杆，方向与直觉相反 | 契约 `GateStatus` 为 OPENED / CLOSED / OPENING / CLOSING / STOPPED / FAULT / UNKNOWN | 去掉 lockState，枚举名直接对齐契约 |
| 4 | 原因码 `0x00`“无”、`0x17`“启动充电”、车位 `0x22`“请求充电”作为正式枚举值 | PRD 8.3：充电相关码忽略 | 充电码按“忽略”处理，`0x00` 映射为 `UNKNOWN` 或单独的“无”，不进入操作记录的触发方式 |
| 5 | `Hex.encode` 输出小写连续串 | 契约 `RawFrame`：十六进制大写、字节间空格 | `raw_frame` 入库与接口输出统一用 `dump` 格式 |
| 6 | 动作原因的告警判断只有遇阻、红外 | PRD 8.4：`E3`、11、12 均为失败并告警 | 在状态机层统一判定，编解码只提供 `isFailure()` 一类的查询 |

单测要补：PRD 8.2 表中全部示例（含下行四条）、方向错用时的行为、版本帧、回显帧、未知码。

### 3.2 指令状态机（重写）

与 PRD 冲突的四处：

| # | WorkBuddy 行为 | PRD 要求 |
| --- | --- | --- |
| 1 | 设备不在线时仍下发，靠 broker 持久会话排队，返回 `queued`，5 分钟后判超时 | 5.3④ 不在线**不排队下发**，直接返回 `DEVICE_SLEEPING` / `DEVICE_OFFLINE` |
| 2 | 设备锁 TTL 20 秒，下发后在 `finally` 中立即释放；执行中可再下一条指令 | 5.3③ 有未完成指令时返回 `COMMAND_IN_PROGRESS`；V3 已用 `uk_command_inflight` 在库里兜底 |
| 3 | 只有 pending → sent → success / timeout；不处理“开闸中 / 关闸中”，不处理 `E3`、遇阻、红外 | 8.4：待下发 → 已下发 → 执行中 → 成功 / 失败 / 超时；`E3`、11、12 为失败 |
| 4 | “已在目标态”直接用缓存闸位判断，不看缓存时间 | 5.3② 缓存 30 秒内由状态帧刷新才可直接判定，否则先查询 |

其他问题：

- 幂等键固定为 `sn:action`，不能区分用户的两次合法操作；契约要求客户端在请求体传 `idempotencyKey`，库里是 `uk_command_idempotency (device_id, idempotency_key)`。
- 确认逻辑跑在进程内线程池，服务重启即丢失，只靠对账兜底。
- 动作模型 `up` / `down` / `open` 与契约 `GateAction` 的 OPEN / CLOSE 不一致；“常开模式”不在一期范围。
- 控制域里混入了审计与后台查询，`iot` 模块按 dev-plan 不应感知用户与权限。

可借鉴：`DeviceTransport` 把“下发”和“等待结果”拆成两个动作；300 ms 轮询查询直到到位帧；`CommandLock` 的 Lua 解锁。新状态机建议以 `control_command` 的状态为唯一事实来源，轮询任务按“指令 ID + 截止时刻”调度，重启后由 IOT-08 从库里恢复。

### 3.3 对账（重写）

- 只把缓存闸位与目标比对：一致判成功，超过 `queuedTimeoutMs`（按 5 分钟排队设计）判超时；从不判失败。
- PRD 8.4⑤ 要求按设备最新状态补齐结果或判超时，超时为 15 秒；重启后需恢复未终结指令（IOT-08）。
- 每批只取 50 条，无分页游标，指令积压时会长期漏扫。
- 可保留：`@Scheduled(fixedDelay)` + 内部吞异常的写法、“比对时间窗 now − 2 s”避免与正在确认的指令抢占。

### 3.4 在线判定（改造）

可沿用：在线 / 休眠 / 离线三态、60 秒扫描、阈值从系统参数读取、连接事件异常不影响 MQTT 主链路。

必须修改：

| # | WorkBuddy 行为 | PRD 8.5 |
| --- | --- | --- |
| 1 | 扫描只做单向推进（在线 → 休眠 → 离线），收到状态帧直接置在线 | 每次按优先级重新判定：离线（`last_seen_at` > 24 h）→ 休眠（最近连接事件为断开，或 > 10 min）→ 在线 |
| 2 | 只有状态帧刷新 `last_seen_at`，回显帧、版本帧不刷新 | 任意上行帧和 EMQX 连接事件都刷新；断开事件不刷新 |
| 3 | 连接事件不落库，只改在线态 | `device_runtime.last_conn_event` 需落库，判定依赖它 |
| 4 | 判定只在扫描时和连接事件时 | 三个时机：上行或连接事件、每 60 秒扫描、控制下发前 |
| 5 | `OnlineState` 含 FAULT | 契约 `OnlineState` 只有 ONLINE / SLEEP / OFFLINE；故障在 `GateStatus.FAULT` 表达 |
| 6 | 连接事件来自订阅 `$SYS/brokers/+/clients/+/#` | dev-plan IOT-05 用规则引擎或 Webhook；`$SYS` 方案可作为备选，需在 EMQX 5 开启系统事件消息 |
| 7 | 设备上线时不触发查询 | 8.7 连接事件后立即下发查询 |

建议把判定写成纯函数 `evaluate(lastSeenAt, lastConnEvent, now, thresholds)`，三个时机都调用它，单测覆盖优先级。

### 3.5 批量导入与激活码

导入（改造）：

- 列不一致：WorkBuddy 为 SN、IMEI、型号、分组、车位号、批次；PRD 5.1 为 SN、IMEI、蓝牙 MAC、型号、批次。需加 MAC 的格式、唯一性和文件内重复校验，去掉分组与车位号。
- SN 规则不一致：WorkBuddy 为 `^[A-Z0-9-]{10,20}$`；契约 `Sn` 为 `^[A-Z0-9]{8,32}$`。以契约为准，导入与单条录入共用一处定义。
- 可复用：行规范化（去 BOM、全角空格、IMEI 去分隔符）、Luhn 与校验位工具、按 500 一批的 `IN` 查询、5 MB / 5000 行上限、异步任务 + 轮询的交互。
- 失败行与印刷文件：PRD 要求失败行可导出修正、印刷文件只能导出一次；V5 的 `import_task` 已有 `failed_detail` 与 `print_exported_at`，WorkBuddy 的独立失败表不再需要。
- 异步执行用的线程池在重启时会丢任务；需把 RUNNING 状态的任务在启动时置为 FAILED 并提示重新导入。

激活码（重写）：

- 只存无盐 SHA-256，且另存了激活码前 4 位（`activate_code_prefix`，用于界面脱敏显示）。字符集 32 个，剩余 4 位只有 32⁴ ≈ 105 万种组合，数据库一旦泄露可在秒级还原全部激活码。即使不存前缀，8 位全空间约 1.1 × 10¹² 种，无盐 SHA-256 也可被 GPU 在短时间内穷举（注释里“36 万亿”的估算有误）。
- 比对用 `String.equals`，非恒定时间。
- 新方案：用慢哈希（如 bcrypt / Argon2）或带服务端密钥的 HMAC-SHA256，比对用恒定时间函数；不存任何明文片段。V1 的 `activate_code_hash VARCHAR(255)` 已能容纳这两种格式。
- 可复用：去掉 0 / O、1 / I 的字符集与 `SecureRandom` 生成逻辑。

### 3.6 DTU 模拟器（用 Java 重写）

现状：

- 一个进程模拟一台设备；不模拟遇阻、红外、电机故障、超时、断线。
- 抬杆 / 落杆后直接回“开闸中 / 关闸中”状态帧，**不发 6 字节回显帧**，测不出“回显不算成功”。
- 落杆的原因码写成 `0x04`（地感），平台落杆应为 `0x16`；查询回包的原因码固定 `0x00`，丢失最近一次动作原因。
- 心跳直接发状态帧，等于默认闸板会主动上报，而这正是 PRD 12.1 第 10、11 项待确认的事项。
- 编解码在 Node 与 Java 各有一份，README 要求“改一边，另一边要同时改”，只能靠人工同步。

dev-plan IOT-03 要求多设备并发，并可注入到位延迟、E3、遇阻、红外、超时、断线、回显帧。差距大，按 IOT-03 重写更省事。

建议用 Java 实现，放在 `tools/dtu-sim`，直接依赖 `server/iot` 的编解码，只保留一套协议实现；集成测试可以在同一 JVM 里启动模拟器。可保留 Node 版的“两段式动作”思路、环境变量清单和日志格式。

### 3.7 MQTT 接入（改造）

可沿用：主题模板 `parking/up/{imei}` / `parking/down/{imei}`、QoS 1、启动时 broker 不可用不阻断启动并每 10 秒重试、断连超过 2 分钟重建客户端、从主题末段取 IMEI。

需要处理：

- **离线排队**：WorkBuddy 依赖 `cleanSession=false` 让 broker 暂存指令（注释写明“省掉了自己写指令队列”）。只要 DTU 也用持久会话，云端发给离线设备的 QoS 1 消息就会被 EMQX 暂存，设备重连后执行，正是 PRD 5.3④ 要避免的情况。云端下发前必须先判定在线；IOT-04 还应给下行消息设置 MQTT 5 消息过期时间（如 15 秒），需实测 EMQX 对 MQTT 3.1.1 客户端是否同样生效。
- Paho v3 不支持 MQTT 5 属性；IOT-04 选型时需改用支持 MQTT 5 的客户端（Paho mqttv5 或 HiveMQ MQTT Client）。
- 一机一密认证、TLS 8883 未实现。

### 3.8 事件分区（复用）

`EventPartitions` 的命名（`pYYYYMM`）、边界计算（下月 1 日，`TO_DAYS`）与 V3 的 `device_event` 完全一致；`EventPartitionService` 每天 03:10 补未来分区、删除超过保留期的分区。搬入时把兜底分区名 `pmax` 改为 `p_future`，保留期按 PRD 的 ≥ 180 天配置。这正好覆盖 INF-04 遗留的“分区滚动任务”，建议随 IOT-06 落地。
